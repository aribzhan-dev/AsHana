# IDENTITY-01 — пользователи, вход, сессии и роли

> Исторический результат этапа. В [UI-01](UI-01.md) владелец уточнил вход по логину и паролю.
> Телефон теперь необязательный контакт; правила ниже о телефонном входе заменены
> [ADR-0008](../docs/architecture/decisions/0008-staff-login-and-ui.md).

Статус: реализовано и проверено. Начало: 20.10.2026, по запросу владельца.
Требования: R11–R16, R18; backend ownership/CSRF/rate limit из backlog.

## Приёмка

- Мобильный KZ-телефон, Unicode-имя, пароль 12–128 символов для сотрудников.
  Публичной регистрации нет: аккаунты создаёт admin или локальная bootstrap-процедура.
  Клиент заказывает без аккаунта; checkout реализуется в ORDERS-01.
- Argon2id, одинаковая ошибка неверных учётных данных; ограничение попыток в PostgreSQL.
- Случайная HttpOnly cookie, только hash сессии в БД, абсолютный TTL 12 часов.
  Logout, просмотр и отзыв собственных сессий; чужие сессии недоступны.
- Origin и CSRF проверяются для всех изменяющих identity-запросов, включая login.
  Secure cookie вне local/test; токены не сохраняются в localStorage.
- Роли kitchen/cashier/storekeeper/manager/admin, deny-by-default.
  Назначение ролей только admin, с аудитом и отзывом сессий изменённого пользователя.
  Нельзя удалить последнего admin; конкурентные изменения сериализуются.
- Первый admin создаётся локальной CLI-процедурой с getpass, без стандартного пароля.
- Русские формы, связанные ошибки, paste/IME, password toggle без submit и потери
  значения; обе темы, клавиатура и ширины 360/390/768/1280/1440.
- Новая миграция после FOUNDATION-01; старые ревизии не меняются.
  Unit, PostgreSQL integration, browser, lint/typecheck/build; документация и самопроверка.

## Границы и решения

Существующие заказы и платежи ещё не реализованы: ownership проверяется на сессиях.
Реальные SMS, подтверждение владения телефоном и восстановление через внешний канал
не подключаются. Demo не притворяется отправкой SMS; на экране видна соответствующая пометка.
Подтверждено владельцем: только мобильные номера Казахстана; регистрации клиентов нет.
Identity обслуживает сотрудников. Все аккаунты локального стенда демонстрационные.

План: domain/application/ports → PostgreSQL/UoW/миграция → HTTP-защита →
UI/OpenAPI → проверки → статус. Риски: гонки создания сотрудников и смены ролей,
утечки credentials в ошибках/логах/артефактах, смена роли при живой сессии.
Локальные стенды изолируются; volumes не удаляются; Git и публикации не выполняются.

## Реализация и свидетельства

- `backend/src/ashana/modules/identity/`: чистый domain, application use cases/ports,
  PostgreSQL UoW, Argon2id/KZ adapters, FastAPI transport.
- `backend/migrations/versions/0002_identity.py`: шесть таблиц, constraints, пять ролей,
  защита audit и каталога ролей от изменения runtime-пользователем.
- `frontend/src/pages/StaffPage.tsx`: вход, кабинет и admin-формы; общие API/Field/RoleFields.
- `backend/tests/test_identity*.py`: валидация/пароли/settings/ошибки и четыре сценария
  на настоящем PostgreSQL, включая конкуренцию и rollback.
- `frontend/tests/identity*.test.*`, `tests/e2e/identity.spec.ts`: UI/API-контракт и браузер.
- `scripts/check_foundation.py --identity --web-port 18081 --api-port 18001`:
  новый volume, переход baseline → identity, повторный upgrade, привилегии,
  отказ/восстановление API/БД, integration и браузер.

Самопроверка исходников обнаружила несовместимость обработчика ошибок с ModelField новой
версии FastAPI: исправлено, добавлен тест на 422 без раскрытия входных данных. Проверены
границы импортов, отсутствие паролей/токенов в ответах и логах, обязательность CSRF,
backend-проверки ролей/ownership, оба режима темы и доступность password toggle.
Внешние публикации, Git-операции, реальная SMS и внешние миграции не выполнялись.

Ограничения: только локальный demo, без recovery/SMS и бизнес-модулей; полный WCAG-аудит,
другие браузеры, нагрузка и процент покрытия не измерялись. Сроки очистки служебных записей
и trusted proxy требуют решения перед пилотом. Итоговые команды и стенд — в текущем этапе.
