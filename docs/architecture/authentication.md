# Аутентификация

Основа реализована в IDENTITY-01, идентификатор входа уточнён владельцем в UI-01. Решение владельца от 20.10.2026: клиент не регистрируется
и не входит в аккаунт; он открывает сайт и оформляет заказ. Identity обслуживает только
сотрудников. Аккаунт сотрудника создаёт администратор. Публичного `/auth/register` нет.
Оформление гостевого заказа относится к ORDERS-01 и ещё не реализовано.

## Вход сотрудников

Вход по **логину и паролю**, которые выдаёт администратор. Телефон не участвует во входе.
Логин: 3–40 ASCII-символов, начинается с латинской буквы, далее буквы/цифры/._-;
внешние обычные пробелы удаляются, регистр не различается. Уникальность защищена в БД.
Одинаковая ошибка неверного логина/пароля не раскрывает наличие аккаунта.

Телефон необязателен и используется только как контакт. При заполнении backend (`phonenumbers`)
и frontend (`libphonenumber-js/max`) проверяют валидность, регион KZ и тип MOBILE.
Один контактный номер может быть у нескольких сотрудников. SMS не отправляется и не требуется
для локального входа по логину. Имя — Unicode, пароль — 4–128 символов без trim (минимум снижен с 12 до 4 по решению владельца 24.10.2026).
Argon2id: memory_cost=65536 KiB, time_cost=3, parallelism=4; при входе возможен rehash.
Неизвестный пользователь проходит dummy hash-проверку, ошибка входа едина.

Сессия — случайный непрозрачный токен (32 случайных байта) в HttpOnly cookie.
В PostgreSQL хранится только SHA-256 токена. Абсолютный срок — 12 часов без продления
при активности; повторный вход заменяет предъявленную сессию. Logout и отзыв немедленно
запрещают использование токена. Доступны список и отзыв только собственных сессий.
Роли читаются из БД при каждом действии; изменение ролей отзывает все сессии сотрудника.

Frontend/API работают с одного origin. Cookie SameSite=Lax, Path=/, без Domain;
Secure и префикс __Host- обязательны в production. Local/test допускают HTTP loopback.
Все изменяющие запросы, включая вход, проверяют точный Origin, Sec-Fetch-Site и CSRF.
До входа выдаётся случайная HttpOnly CSRF-cookie; после входа CSRF-токен связан с сессией
отдельным hash с domain separation. Он передаётся в заголовке, bearer-токен не доступен JS.
Ответы identity имеют Cache-Control: no-store; localStorage хранит только тему.

Ограничение входа сохраняется в PostgreSQL: 10 попыток на нормализованный логин и 60 на адрес за
15 минут; неуспешный вход не откатывает счётчик. API не доверяет X-Forwarded-For.
В локальном Compose за nginx лимит адреса общий для proxy; перед внешним пилотом нужны
проверенная конфигурация trusted proxy и отдельные лимиты на edge. Срок очистки старых
сессий, audit и ключей rate limit необходимо согласовать с политикой хранения данных.

## Локальные аккаунты

Первый admin создаётся `python -m ashana.bootstrap.admin` с вводом пароля через getpass,
без пароля по умолчанию. Повторный bootstrap запрещён. Он получает admin + manager;
в дальнейшем роли назначаются явно. Все аккаунты этого этапа имеют is_demo=true.
Settings запрещает demo_identity=true и cookie_secure=false в production; production
не принимает demo-аккаунты. UI помечает demo-аккаунт; телефонная информация отделена от credentials.

До внешнего пилота требуются реальные onboarding/recovery, HTTPS и эксплуатационные
проверки. Восстановление пароля и внешний onboarding сейчас отсутствуют.
Пароли, cookie и токены не попадают в ответы, аудит или логи. См.
[локальные команды](../engineering/local-development.md) и [валидацию](../product/validation-and-localization.md).

Переход со старой схемы описан в [ADR-0008](decisions/0008-staff-login-and-ui.md).
Существующим аккаунтам назначается staff_ + UUID без дефисов, пароли/роли/сессии сохраняются.
