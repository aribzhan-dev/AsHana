# ADR-0010 — версии рецептов и атомарный выпуск

Статус: техническое решение реализации PRODUCTION-01, 21.10.2026.
Не устанавливает нормы питания, сроки хранения или метод финансовой себестоимости.

## Решение

Одна собственная позиция inventory_items объединяет версии своего рецепта. Отдельная изменяемая
таблица «шапки рецепта» пока не нужна: production_recipes содержит неизменяемые версии с
unique(output_item_id, version), production_recipe_lines — нормы на весь плановый выход.
Размер порции означает массу/объём готового продукта, а не вес сырого ингредиента. Версия
сохраняет инструкцию, автора и время. Позиции справочника inventory пока тоже неизменяемы.
Новый рецепт использует previous_version=0, новая версия — номер просмотренной версии.
Advisory lock по output_item_id защищает создание последовательного номера; устаревшая форма
получает STALE_RECIPE. Выпуск может явно выбрать любую сохранённую версию.

production_batches связан 1:1 с готовой inventory_batches (один UUID); хранит recipe_id,
фактический выход, автора и время. production_consumption хранит фактический расход по
конкретным партиям и ссылки на immutable inventory_movements. Повтор одного ингредиента
в рецепте запрещён; в выпуске он может быть распределён между несколькими разными партиями.
Все ингредиенты выбранной версии обязательны, лишние запрещены; фактические количества
не обязаны совпадать с нормой. Нет автоматического масштабирования нормы в фактический расход.

Production UoW получает inventory application port и production repository, работающие
на одном SQLAlchemy Connection/transaction. Composition root связывает модули;
domain/application не импортируют ORM или presentation. Сначала shared identity lock и
проверка production.manage, затем actor/operation/key lock, затем партии в порядке UUID.
Пригодность и срок проверяются по серверным часам после получения всех row locks.
Партия должна быть активна и иметь достаточно свободного сырья. Резерв не затрагивается.
Подтверждение сотрудника о пригодности обязательно и не заменяет серверную проверку.

В одной транзакции: production_consume движения и уменьшение сырья, production_output и
готовая партия, запись выпуска/расходов, аудит и idempotency record. Общие inventory_audit и
inventory_requests используются через порт склада с отдельными operation names
recipe_created / production_confirmed. Их UPDATE/DELETE уже запрещены runtime-роли.
Новые четыре таблицы производства также доступны runtime только для SELECT/INSERT.

Любая ошибка полностью откатывает транзакцию. Одинаковый actor/operation/key с тем же payload
возвращает сохранённый результат; с другим — конфликт. Права проверяются и при replay,
включая новую сессию после смены роли. У recipe/create и production/confirm разный scope.
UI удерживает ключ неизменённых данных при потере ответа и блокирует двойную отправку.
После закрытия формы/перезагрузки ключ не сохраняется: сначала проверить историю выпуска.

Срок готовой партии вводит сотрудник; момент выпуска ставит сервер. Порции/штуки целые,
сырьё NUMERIC(18,6), ввод до трёх дробных знаков с явной конверсией g→kg/ml→l.
Готовая партия имеет техническое total_cost_minor=0; себестоимость не рассчитывается из
стоимости исходных партий и не считается нулевой фактической себестоимостью. API отдаёт
item_kind, склад показывает для собственной продукции «Себестоимость выпуска пока не рассчитана».
Финансовые отчёты должны учитывать это ограничение на своём этапе.

## Исправления и границы

Выпуск и расход не редактируются и не удаляются. Ошибка фактического готового остатка
исправляется отдельным складским пересчётом/списанием с причиной уполномоченным сотрудником;
batch_id связывает движение с выпуском. Ошибка учёта сырья также требует отдельного
пересчёта и причины, а не автоматического возврата приготовленных ингредиентов.
Если исправление затрагивает резерв, склад его отклоняет. Разбор связанных заказов будет
реализован вместе с заказами. Продажи/отмена заказа не должны вызывать производство повторно.

Альтернатива — вызвать два независимых сервиса склада с отдельными commit — отвергнута:
при сбое между списанием и приходом учёт расходился бы. Изменяемый рецепт без версии
не позволяет восстановить технологию прошлого выпуска. Автоматическая себестоимость и WIP
требуют дополнительных бизнес-решений и не входят в PRODUCTION-01.
