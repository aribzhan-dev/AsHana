# ADR-0008: логин сотрудника и общие UI-компоненты

Дата: 20.10.2026. Статус: продуктовые ограничения подтверждены владельцем;
реализовано и проверено в UI-01; результаты в [текущем этапе](../../../tasks/current-sprint.md).

## Контекст и решение

Владелец уточнил: администратор создаёт сотрудников и лично выдаёт им логины и пароли.
Телефон — справочная контактная информация. Клиентской регистрации по-прежнему нет.
Поиск сотрудника и вход используют отдельный login. Контактный телефон необязателен,
при заполнении проходит KZ MOBILE-проверку, не обязан быть уникальным и не даёт права входа.

Техническая политика login: 3–40 ASCII-символов, первый — латинская буква, остальные —
латинские буквы, цифры, точка, дефис, подчёркивание. Внешние обычные пробелы удаляются,
регистр приводится к нижнему. В БД — unique и CHECK; одинаковые логины в разном регистре
конфликтуют. Password/CSRF/session/role guards сохраняются.

Миграция 0003_staff_login не меняет предыдущие ревизии, UUID, хэши паролей, роли или сессии.
Старым аккаунтам присваивается уникальный `staff_` + UUID без дефисов (38 символов).
Старый телефон сохраняется; login добавляется в ответы профиля и admin-поиска.

UI-01 выделяет общие компоненты без новой UI-зависимости. SVG-иконки декоративны,
кнопки имеют русские доступные имена. Темы light/dark/system выбираются в native dialog,
открываемом компактной кнопкой с иконкой; фокус ограничен диалогом и возвращается при закрытии.
Placeholder дополняет постоянную подпись. Identity-формы используют общие компоненты,
но правила ролей и серверные вызовы остаются в feature-слое и backend.

## Альтернативы и последствия

Вход по телефону исключён уточнением владельца. Публичная регистрация не добавляется.
Старый логин на основе телефона не сохраняется как скрытый alias, чтобы контакт не оставался
credential. До обновления существующего стенда оператор должен сообщить сотрудникам новые
логины. Хэши паролей и действующие сессии сохраняются. Для пустого стенда bootstrap сразу
запрашивает новый login; пароля по умолчанию нет.

Готовая UI-библиотека пока не требуется: native controls и CSS tokens покрывают текущие формы.
ProductCard и OrderStatus будут реализованы с предметными контрактами CATALOG/ORDERS,
а QuantityInput подготовлен без подключения к складским/заказным операциям.
