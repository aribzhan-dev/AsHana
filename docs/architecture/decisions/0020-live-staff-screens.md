# ADR-0020: живые экраны кухни и кассы через WebSocket

Статус: принято по запросу владельца 22.10.2026. Реализует [ADR-0005](0005-outbox-and-online-only.md)
в части WebSocket. Миграция `0014_realtime`.

## Решение

- Триггеры PostgreSQL на `order_events`, `pos_attempts`, `inventory_movements` и
  `catalog_entries` вызывают `pg_notify('ashana_events', …)`. NOTIFY доставляется только после
  commit, поэтому откатанные изменения экраны не видят.
- Каждый процесс API держит одно соединение `LISTEN` (роль `ashana_app`) и раздаёт сигналы
  подключённым экранам через in-process hub. Несколько процессов API работают, так как
  каждый слушает PostgreSQL сам; общий in-memory список между процессами не нужен.
- `GET ws /api/v1/staff/events`: сессия сотрудника из cookie, проверка Origin по
  `allowed_origins` (защита от cross-site WebSocket), права — `orders` для `kitchen.read`,
  `pos` для `pos.sell`, `stock` для кассы, кухни и склада. Раз в 60 секунд сессия
  перепроверяется: отозванная сессия или изменённые права закрывают поток.
- Сообщение — только тема, вид события и идентификатор; без кода получения, телефона и сумм.
  Экран получает данные обычным HTTP-запросом.
- Клиент: одно соединение на страницу, переподключение с нарастающей паузой до 30 секунд,
  после подключения — полная перезагрузка данных. Пока соединения нет — опрос каждые
  15 секунд, при соединении — страховочный опрос раз в 60 секунд. Видимый индикатор связи.
- Кухня: плашка «Новый заказ №…» и звук, который сотрудник включает сам (политика браузера).
- nginx проксирует Upgrade только для этого пути с увеличенным таймаутом чтения.

## Альтернативы

Отдельный брокер (Redis, Kafka) избыточен для одной столовой. Опрос раз в секунду нагружает БД.
Server-Sent Events возможны, но WebSocket уже предусмотрен ADR-0005.

## Последствия

Каждый процесс API занимает одно дополнительное соединение с БД. Гостевые страницы
по-прежнему обновляются опросом раз в 15 секунд (изменено в [ADR-0022](0022-guest-live-and-photos.md): гость получает свои события по WebSocket).
