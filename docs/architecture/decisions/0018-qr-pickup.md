# ADR-0018: получение заказа по QR-коду

Статус: принято по запросу владельца 22.10.2026 (вариант «QR у посетителя + сканер на стойке»).
Уточняет [ADR-0013](0013-serving-ready-food.md); правила однократной выдачи не меняются.

## Контекст

Сотрудник вводил 8 символов кода с экрана посетителя вручную: медленно и с ошибками.
Владелец выбрал вариант, где посетитель показывает QR-код, а стойка выдачи его сканирует.

## Решение

- Посетитель видит QR в карточке активного заказа (`/orders`, вкладка «QR»).
  Содержимое: `ASHANA1:<UUID заказа>:<код получения>`. Код по-прежнему виден только владельцу
  гостевого cookie; рабочие DTO и Telegram код не возвращают.
- Новая страница `/staff/scan` («Выдача по QR», право `orders.fulfil` для выдачи,
  `kitchen.read` для просмотра). Источники: камера браузера (jsQR) или ручной USB/Bluetooth-сканер,
  работающий как клавиатура, либо вставка текста.
- Новый endpoint `GET /api/v1/orders/staff/{id}` с `kitchen.read` возвращает рабочий DTO без кода.
  Неоплаченные оформления и чужие идентификаторы — 404.
- Выдача идёт через существующий переход `completed` с `expected_version`, idempotency key и
  серверной проверкой кода, лимитом попыток и блокировками ADR-0013.
- Короткий номер «№1234» выводится из UUID только для отображения; он не уникален и не
  используется для поиска или доступа.

## Альтернативы

QR на стойке, который сканирует посетитель, не подтверждает владельца заказа: его может
отсканировать любой. Публичный поиск по коду противоречит ADR-0013. Обе альтернативы отклонены.
QR на стойке можно добавить позже только как сигнал «я пришёл», не как подтверждение выдачи.

## Последствия

Камера работает на `localhost` или по HTTPS; на планшете в локальной сети без HTTPS нужен
ручной сканер. Добавлены зависимости `qrcode` и `jsqr`. Вне QR ручной ввод кода сохранён.
