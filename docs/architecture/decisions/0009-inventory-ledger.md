# ADR-0009: склад по партиям и журнал движений

Дата: 21.10.2026. Статус: техническое решение реализации INVENTORY-01.
Основание — просьба владельца продолжить проект и требования склада; это не утверждение
норм хранения, себестоимости или будущей политики заказов.

## Решение

Inventory владеет inventory_items, inventory_batches, inventory_movements,
inventory_audit и inventory_requests. Identity передаёт principal через application-контракт;
composition root связывает проверку с той же PostgreSQL connection, что и складская транзакция.
Domain не импортирует ORM/HTTP. Доступ к каждому запросу требует inventory.manage;
admin без manager/storekeeper не получает операционного доступа.

Базовые единицы kg/l/pcs/portion. Ввод допускает до 3 десятичных знаков; g/ml переводятся
явным множителем 0.001. NUMERIC(18,6) сохраняет точность; шт/порции целые, максимум
999999999 базовых единиц в партии. UI явно нормализует запятую в точку; API принимает
десятичную строку с точкой без экспоненты. Деньги — общая стоимость прихода, BIGINT в тиынах,
до 999999999999. Стоимость единицы и списания по методу оценки не рассчитываются.

Приход создаёт партию + первое движение + аудит + результат идемпотентности в одной
транзакции. Сотрудник задаёт источник, дату прихода и обязательный срок пригодности;
истёкший приход допустим для фактического учёта, но available=0. Собственный готовый
продукт нельзя приходовать вручную: нужен будущий use case производства.

Списание уменьшает физический остаток. Инвентаризация записывает фактическое количество
и разницу (включая нулевую), а не заменяет историю. Причина обязательна. При полном списании
партия закрывается; счёт с нулём остаётся исправляемым инвентаризационным состоянием.
Приостановка/возобновление тоже создают движение с нулевой дельтой и причиной.
Истёкшие партии нельзя возобновлять. Доступность вычисляется по серверному времени.

Изменения блокируют строку партии FOR UPDATE и проверяют expected_version. Два пересчёта
на одной версии не перезаписывают друг друга: второй получает STALE_BATCH. Каждая версия
имеет ровно одно движение; UNIQUE(batch_id, version) и CHECK(before+delta=after) страхуют БД.
CHECK on_hand>=reserved>=0 запрещает уничтожить резерв. Сейчас резервов ещё нет; будущие
заказы/касса/производство обязаны использовать ту же блокировку и общую транзакцию.
Разбор испорченной зарезервированной партии и уведомления появятся с заказами.

Все изменения принимают UUID Idempotency-Key. Scope: actor+operation+key; hash payload
и сохранённый result записываются атомарно. Advisory lock сериализует только этот scope;
повтор возвращает прежние subject_id/version, другой payload — 409. Перед replay снова
проверяются права и сессия. Общая shared-lock с identity role-change защищает проверку прав
до commit; независимые складские операции не блокируются одной глобальной exclusive-lock.
UI сохраняет ключ при повторе тех же данных в открытой форме после потери ответа.
После закрытия формы/перезагрузки сначала проверить историю: ключ в браузере не сохраняется.

Runtime не имеет UPDATE/DELETE для движений, аудита, idempotency records и справочника;
партию нельзя DELETE. Исправления идут отдельными операциями. Миграция 0004 только
добавляет таблицы, старые записи identity не изменяет. Downgrade требует отдельного плана.

## Альтернативы и ограничения

Один счётчик на товар не позволяет объяснить сроки и историю каждой поставки; выбраны партии.
Float и автоматическое округление исключены из учёта. Инвентаризация без версии опасна при
одновременной продаже/списании, поэтому версия обязательна. Event sourcing не требуется:
остатки обновляются рядом с неизменяемым журналом в той же транзакции.

Справочник пока неизменяем: ошибочное название требует отдельной будущей операции с аудитом.
Поиск и фильтры можно развить позже; списки имеют ограничение и пагинацию. Временная политика
хранения idempotency/audit не добавляется без согласования срока хранения данных.
