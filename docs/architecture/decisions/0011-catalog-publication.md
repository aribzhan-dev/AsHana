# ADR-0011 — публикация меню по готовому остатку

Статус: техническое решение CATALOG-01 от 21.10.2026 в пределах порученного этапа.
Точные часы питания, рецептуры и цены владелец не задавал: их вводит управляющий.

## Решение

Catalog владеет catalog_periods, catalog_entries и catalog_audit. Отдельную таблицу products
пока не создаём: идентичность, название и единица уже принадлежат inventory_items. Карточка
в конкретном периоде содержит описание, подпись порции, цену и флаг публикации. Это исключает
две независимые связи между товаром, рецептом и складом; будущая общая карточка возможна
отдельной миграцией. В одном периоде товар уникален; архивирование заменено снятием публикации.

Период — именованный интервал не более суток, без фиксированных enum breakfast/lunch и часов.
На staff-экране фильтр по дате начала Алматы, на гостевом — активный серверный интервал.
Публичная позиция требует публикации периода и записи и положительного свободного готового
остатка. Остатки не копируются в catalog и не распределяются между периодами.

Repository каталога имеет согласованную read-only SQL-проекцию inventory_items/inventory_batches.
Она не импортирует чужую ORM metadata и ничего не пишет в склад; reference-таблицы не мигрируются
каталогом. Это позволяет одним statement атомарно фильтровать активность/пригодность и агрегировать
остаток до pagination. Альтернатива — отдельные запросы или сетевой inventory API: они дают
разные снимки, усложняют фильтрацию и оставляют пустые страницы. Материализованный остаток
отклонён из-за риска запаздывания. Владельцем количества остаётся inventory.

UoW инъецирует InventoryRepository через composition root для разрешённого чтения справочника
и существующего контракта идемпотентности inventory_requests. Actor + catalog operation + key
образуют отдельный scope. Catalog не пишет складские движения и имеет собственный audit
before/after. При расширении количества модулей общий журнал запросов можно выделить отдельно;
сейчас это повторное использование порта без копирования реализации.

Изменения period/entry — optimistic version плюс row locks, audit и replay в одной транзакции.
Право catalog.manage повторно проверяется при replay; shared identity lock блокирует гонку
с отзывом ролей. Защита runtime запрещает удаление карточек/периодов и изменение аудита.

## Последствия

Публичный ответ — снимок на generated_at, no-store, без внутренних складских/личных полей.
UI обновляет его каждые 30 секунд/при focus и скрывает данные при ошибке. Просмотр не резервирует.
В ORDERS-01 сервер обязан повторно проверять публикацию, период, цену, свободные партии и слот,
атомарно резервировать их и сохранять снимок карточки в составе заказа. Сам CATALOG-01
не предотвращает будущую конкуренцию продаж: это задача общей складской транзакции заказа.
