# ADR-0013: комплектация готовой еды и однократная выдача

Статус: реализация KITCHEN-01, 21.10.2026. Владелец уточнил, что еда готовится заранее,
а по заказу её только порционируют/комплектуют и выдают. Производство отдельное.

Состояния: confirmed → preparing → ready → completed. preparing означает «Комплектуется»,
не «Готовится». Комплектация/готовность не меняют склад; клиентская отмена после начала
комплектации запрещена. kitchen.manage позволяет первые два перехода; orders.fulfil — выдачу.
Admin не получает эти права автоматически. Нужные роли можно совместить у одного сотрудника.

Код получения — 8 случайных hex-символов, генерируется при успешной mock-оплате; виден только
владельцу заказа. Сотрудник вводит код с его экрана в подтверждении выдачи. Рабочие DTO и Telegram
код не возвращают. Код проверяется для конкретного UUID заказа и не заменяет staff-сессию/CSRF.
Поиск гостевых заказов по коду публично не предусмотрен. Есть лимит попыток выдачи на сотрудника.

Переход проверяет разрешение, scoped idempotency, блокирует checkout_drafts, проверяет состояние
и expected_version, затем блокирует все зарезервированные партии по UUID. Проверка пригодности
выполняется после блокировок по серверному времени. Сбой одной партии запрещает всю выдачу.
Completed атомарно уменьшает on_hand и reserved на одну и ту же величину, закрывает allocations,
добавляет mock_fulfil movements, consume reservation events, inventory audit, order event,
outbox и replay. Сырьё и production tables не изменяются. Слот остаётся занятым как обслуженная
нагрузка, а не открывается для нового заказа.

Два сотрудника сериализуются блокировкой заказа: первый выдаёт, второй получает конфликт.
Тот же успешный idempotency key возвращает текущее состояние без повторного расхода;
новый ключ не позволяет ещё раз выдать completed. Ошибка аудита/уведомления откатывает также
изменения партий и состояния. Кнопка UI — удобство, защита находится в backend/транзакции.

Миграция 0008_kitchen добавляет pickup_code и расширяет CHECK действий журналов; существующим
оплаченным активным заказам назначает случайный код. Старые миграции не переписываются.
Новый статус отражается через polling, Telegram использует существующую долговечную очередь.

Альтернативы: создавать production при выдаче неверно и повторно списало бы сырьё; снимать
резерв отдельной транзакцией позволило бы другой покупке забрать обещанный товар; запрещать
повтор только disabled-кнопкой не защищает от двух устройств. Эти варианты отклонены.

Ограничения: пока все заказы mock, выдача явно ДЕМО и не доказывает оплату настоящей еды.
Нет автоматической замены испорченной партии, no-show и компенсирующего возврата после выдачи;
эти операции требуют отдельной согласованной логики. Telegram ещё не подключён к живому каналу.
