# Уведомления и фоновые операции

Предложено: transactional outbox в PostgreSQL; небольшой worker того же приложения
читает зафиксированные события, повторяет доставку при сбое. Kafka/Redis/Celery пока не обязательны.
События `order.confirmed.v1`, `order.ready.v1`, `order.cancelled.v1` содержат event_id,
order_id, occurred_at и версию; без пароля и полного телефона.

WebSocket передаёт сигнал об изменении, HTTP API отдаёт достоверное состояние.
Для первого запуска допустим один API-процесс с worker-задачей и обработкой outbox;
масштабирование на несколько процессов требует отдельного канала fan-out и нового решения.
Не утверждать, что in-memory список WebSocket соединений работает между процессами.

Доставка at-least-once: потребитель устраняет дубли по event_id. При reconnect клиент заново
загружает активные заказы, при недоступном WebSocket использует периодический HTTP refresh.
Сбой сигнала не теряет заказ. Звук включается сотрудником после взаимодействия с браузером;
есть видимый индикатор новых заказов и состояния соединения.

Истечение mock-резерва обрабатывается идемпотентной фоновой задачей и проверяется также
при действиях с заказом; задержка worker не должна позволять оплатить уже истёкший заказ.

Реализованное уточнение ORDERS-01: notification_outbox создаётся в транзакции успешной
mock-оплаты либо отмены оплаченного заказа. Неоплаченные checkout_drafts не отправляются.
Доставка Telegram вынесена в фоновый worker, отключена без конфигурации, имеет lease/retry.
WebSocket пока нет; состояние экранов восстанавливается HTTP polling раз в 15 секунд.
[Ограничения и подключение](../engineering/orders-usage.md).

Реализовано 22.10.2026 ([ADR-0020](decisions/0020-live-staff-screens.md)): триггеры PostgreSQL +
LISTEN/NOTIFY → WebSocket `/api/v1/staff/events` для кухни и кассы. HTTP остаётся источником
данных; без соединения экраны опрашивают API каждые 15 секунд, гостевые страницы — как прежде.
